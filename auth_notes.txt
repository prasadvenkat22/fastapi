================================================================================
1. SETTING A PASSWORD (DO THIS FIRST)
================================================================================

The admin accounts are seeded WITHOUT passwords, on purpose. A password
invented by a migration would either be known to nobody or become a shared
secret sitting in git history.

Local:

    docker compose exec app python scripts/set_password.py venkatangirala@gmail.com

Production (on the droplet, in /opt/fastapi):

    docker compose -f docker-compose.yml -f docker-compose.prod.yml \
        exec app python scripts/set_password.py venkatangirala@gmail.com

It prompts twice, hidden. Minimum 12 characters. The password is never
echoed, never passed as a command argument (where `ps` would expose it), and
never logged — only the bcrypt hash is written to the database.

DO NOT ADD -T. The flag is in most of the compose commands in
deployment_notes.txt and it removes the TTY that getpass needs to hide
typing. With -T the password is printed to the terminal and into your
shell's scrollback. If that happens, set a different password.

The same command CHANGES a password, and is the way back when nobody can
log in at all. For an ordinary forgotten password there are now two better
routes that do not need SSH — see section 6.

A NEW account does not exist to set a password on. Create it first:

    docker compose -f docker-compose.yml -f docker-compose.prod.yml         exec app python scripts/add_user.py someone@example.com admin

add_user.py deliberately does not set a password. The two steps are separate
because creating the row is safe to do over SSH and choosing the password is
not: a password invented on the server has to be transmitted to its owner
somehow, and every way of doing that is worse than the account not having
one yet. An account with no password CANNOT log in — login checks for a null
hash and rejects — so creating the row early is harmless.

================================================================================
2. LOGGING IN
================================================================================

Easiest — the interactive docs:

    http://localhost:8000/docs

Find the "Auth" section, POST /auth/login, "Try it out", fill in email and
password, Execute.

By curl:

    curl -X POST http://localhost:8000/auth/login \
      -H "Content-Type: application/json" \
      -d '{"email":"venkatangirala@gmail.com","password":"<yours>"}'

Response:

    {
      "access_token": "eyJ...",
      "refresh_token": "eyJ...",
      "token_type": "bearer",
      "expires_in_minutes": 15
    }

Use the access token:

    curl http://localhost:8000/auth/me \
      -H "Authorization: Bearer <access_token>"

    -> {"id":5,"name":"venkatangirala","email":"...","role":"admin"}

When the access token expires (15 min), trade the refresh token for a new
pair:

    curl -X POST http://localhost:8000/auth/refresh \
      -H "Content-Type: application/json" \
      -d '{"refresh_token":"<refresh_token>"}'


================================================================================
3. ROLES
================================================================================

    admin    Full access: business records, users, GenAI, AND the trading
             engine. This is the role both seeded accounts hold.
    trader   Trading routes only — scheduler, manual cycles, kill switch.
             Cannot delete customers, users or invoices.
    user     Read access to business records.

A user with role_id = NULL has NO role, which must be read as NO PERMISSIONS,
not as a default grant. Every account created before roles existed has NULL,
so the opposite reading would silently promote all of them.

To assign or change a role, re-run add_user.py with the new role. It
changes the role and leaves the password alone, which is how a promotion or
demotion happens:

    docker compose -f docker-compose.yml -f docker-compose.prod.yml         exec app python scripts/add_user.py someone@example.com trader

Hand-written UPDATE statements were how this used to be done and are how a
role_id ends up pointing at nothing, or an email differs from the login by a
capital letter. add_user.py validates the role exists and lowercases the
email, because login compares it exactly.


================================================================================
4. HOW THE TOKENS WORK
================================================================================

RS256 (asymmetric). The service signs with JWT_PRIVATE_KEY and verifies with
JWT_PUBLIC_KEY. Only this service can mint a token; anything that only needs
to VERIFY one needs the public key alone — which matters if verification ever
moves to a gateway.

Keys are 4096-bit, stored base64-encoded (a raw PEM's newlines do not survive
a .env file), and are DIFFERENT between local and production. They were
previously 512-bit and identical across environments; 512-bit RSA has been
factorable since 1999, so the public key alone was enough to forge tokens.

A JWT IS SIGNED, NOT ENCRYPTED. Anyone holding a token can base64-decode the
payload and read it — the signature proves it was not tampered with, it does
not keep anything secret. The payload therefore carries only:

    sub   user id
    role  role name (or null)
    type  "access" or "refresh"
    iat   issued at
    exp   expires at

Never put a password, API key, or anything sensitive in there.

Tokens are NOT stored server-side. That is the point of JWT — the token
carries its own claims and the signature is checked on arrival. Storing
access tokens would add a database read to every request and discard the only
reason to use JWT.

Two safety details worth keeping:

  - decode_token checks the token TYPE. Access and refresh tokens are both
    validly signed by this service, so a signature check alone cannot tell
    them apart — and a refresh token lives four times longer. Presenting a
    refresh token as a bearer credential is rejected.

  - get_current_user RE-READS the user from the database rather than trusting
    the token's claims. A token stays validly signed until it expires, so an
    account disabled a minute ago would still present a perfectly good one.
    Role is read the same way, so a demotion applies immediately instead of
    lingering for the life of an issued token.

Login failures return ONE message for every cause — unknown email, wrong
password, no password set, disabled account. Distinguishing them would let
anyone enumerate which emails are registered.

Config: JWT_ALGORITHM (RS256), ACCESS_TOKEN_EXPIRES_IN (15 minutes),
        REFRESH_TOKEN_EXPIRES_IN (60 minutes)


================================================================================
5. MANAGING USERS OVER HTTP
================================================================================

All of these require an admin token. Get one from POST /auth/login.

    GET    /users                       list, with role and whether a
                                        password is set
    GET    /users/{id}
    POST   /users                       create WITH a role
    PATCH  /users/{id}                  change role, disable, rename
    DELETE /users/{id}
    POST   /users/{id}/reset-password   issue a temporary password, shown
                                        once, when someone cannot use the
                                        self-service reset in section 6

Create an admin:

    curl -X POST http://<host>/users       -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json'       -d '{"email":"someone@example.com","role":"admin"}'

`password` is optional and usually omitted. Leave it out and the account
exists but cannot log in until its owner sets one — same reasoning as
add_user.py. Include it and it must be at least 12 characters.

GUARDS. Four operations can lock everyone out of every protected route, and
the only way back is a shell on the server, so all four refuse with a 409:
deleting yourself, and deleting, disabling or demoting the only admin who can
actually log in. Disabled admins and admins with no password do not count
toward that last check, because neither can authenticate — counting them
would let the guard pass while leaving nobody able to get in.

THE SCRIPTS STILL WORK and are still the bootstrap path. They talk to the
database directly, so they are how you recover when nobody can log in — which
is exactly the situation an HTTP endpoint cannot help with.

THE OLD ENDPOINTS ARE STILL THERE and are now admin-only:

    POST /CRUD/register/    POST /CRUD/users/    DELETE /CRUD/users/{id}

Prefer /users. UserCreate has no role field, so anything created through the
/CRUD/ pair still lands with role_id = NULL — authenticated, but holding no
permissions on any router. They are kept only so an existing caller does not
break; removing them is worth doing.

6. EMAIL, AND FORGOTTEN PASSWORDS
================================================================================

SETTING IT UP. NOT GMAIL -- DigitalOcean blocks outbound 25, 465 and 587 at
the network level, and Gmail offers no other port. Verified 2026-08-23: the
host itself times out on all three, ufw's OUTPUT policy is ACCEPT with no
SMTP rules, so it is upstream and nothing on the droplet can change it. The
failure is "OSError: [Errno 101] Network is unreachable", never an auth
error, so it looks nothing like a wrong password.

Port 2525 IS open, and SendGrid, Brevo and Mailgun all offer it for exactly
this reason -- each verified with a full EHLO + STARTTLS handshake. Sign up
with one, create an API key, and set:

       SMTP_HOST=smtp.sendgrid.net     (or smtp-relay.brevo.com, smtp.mailgun.org)
       SMTP_PORT=2525
       SMTP_USER=apikey                (SendGrid's literal username; others differ)
       SMTP_PASSWORD=<the API key>
       MAIL_FROM=you@yourdomain
       APP_BASE_URL=https://dataiqsystems.com

No code change is needed for any of them: mailer.py is plain SMTP precisely
so the provider is a configuration choice.

AND NOTE HOW ENV CHANGES TAKE EFFECT. `docker restart app` does NOT re-read
env_file -- variables are fixed when a container is CREATED. Use:

    docker compose -f docker-compose.yml -f docker-compose.prod.yml         --env-file .env.production up -d app

Rebuild FIRST if code changed since the image was built, or the recreate can
drop you back to a stale image.

The Gmail instructions below are kept only because they apply if this ever
runs somewhere without the block:

  1. Turn on 2-Step Verification at myaccount.google.com/security — the
     App Passwords page does not exist until you do.
  2. Create one at myaccount.google.com/apppasswords. It is shown once.
  3. On the droplet, in /opt/fastapi/.env.production:

       SMTP_HOST=smtp.gmail.com
       SMTP_PORT=587
       SMTP_USER=you@gmail.com
       SMTP_PASSWORD=<the 16 characters, no spaces>
       MAIL_FROM=you@gmail.com
       MAIL_FROM_NAME=DataIQ Systems
       APP_BASE_URL=https://dataiqsystems.com

  4. docker restart app

UNCONFIGURED IS SUPPORTED. With SMTP_HOST unset nothing is sent, the
endpoints still work, and the log says "Email NOT sent to ... SMTP is not
configured". Failures never reach the caller either: a password that
changed must not report failure because a mail server blinked.

WHAT GETS SENT
  password changed      after a self-service change AND after an admin
                        reset. Sent even when expected — it is not for the
                        person who did it, it is for the case where it
                        was not them.
  account created       when an admin creates a user at POST /users.
  reset link            in response to /auth/forgot-password.

THE FORGOTTEN-PASSWORD FLOW
  POST /auth/forgot-password   {"email": "..."}   → always 204
  GET  /auth/reset-password?token=...             → the page from the email
  POST /auth/reset-password    {"token","new_password"} → 204

ALWAYS 204, account or not. Anything else makes the one endpoint that must
be public into a way to test which emails are registered. The send happens
in a background task for the same reason — replying only after a successful
send would leak by timing what the status code refuses to say.

Tokens are 32 random bytes, stored as sha256 (not bcrypt: there is nothing
to guess in 32 random bytes, so the slow hash would buy only a slow
endpoint), single-use, and expire in PASSWORD_RESET_MINUTES (30). Spending
one kills every other live link for that account — otherwise an attacker who
triggered a reset earlier still holds a working one after the owner has
recovered. PASSWORD_RESET_MAX_LIVE (3) caps how many an account may hold, so
the public endpoint cannot be used to flood a mailbox.

Verified on 2026-08-23: 204 for both a real and a nonexistent address, a
64-character hash written, second use of a token refused with "already been
used", the other outstanding token marked spent by the first one's use, and
login with the new password returning 200.

A reset link is a credential for the 30 minutes it lives, and this is still
plain HTTP. Until TLS is in place the link can be read in transit by anyone
watching — see section 7 item 1.

7. REMAINING WORK BEFORE AUTH ACTUALLY PROTECTS ANYTHING
================================================================================

  DONE 2026-08-23: dependencies applied in main.py, and POST /CRUD/register/
  is admin-only rather than public.

  1. TLS. The biggest one now. Every token and password crosses the wire in
     plain HTTP, so enforcement raises the bar against a stranger and not
     against anyone who can watch the traffic.

  2. The `user` role does nothing yet. Section 3 promises it read access to
     business records; main.py gives /CRUD/* to admin only. Splitting reads
     from writes needs per-endpoint dependencies across ~40 routes, and
     claiming it in main.py without them would be a lie in the one file
     people check. All four accounts are admins today, so nothing is blocked
     by this — it is a promise the code has not kept, not a broken feature.

  3. Remove POST /CRUD/register/ and POST /CRUD/users/. They duplicate
     /users, cannot assign a role, and the accounts they make hold no
     permissions on any router.

  3. Consider a refresh_tokens table if you want revocation. Access tokens
     are stateless and should never be stored. Refresh tokens are the ones
     worth storing (HASHED, like a password) if you need "log out
     everywhere" or the ability to kill a stolen token before it expires.
     Without it, a stolen refresh token stays valid for its full 60 minutes
     and nothing can be done.

  4. Add TLS. Tokens and passwords currently cross the wire in plain HTTP.


================================================================================
8. TROUBLESHOOTING
================================================================================

401 "Incorrect email or password"
    Most likely no password is set on the account. Run section 1.
    (The message is intentionally identical for every failure cause.)

"/auth/me has nowhere to put the token" (Swagger /docs)
    Correct — no endpoint in Swagger has its own token field. Authorization
    is set ONCE, globally: click the Authorize button at the top right, paste
    the access_token ALONE (no "Bearer" — Swagger adds it), Authorize, Close.
    The padlock beside each secured endpoint then shows closed.

    Running POST /auth/login inside Swagger does NOT apply the token it
    returns. You still have to copy access_token into Authorize by hand.

    No Authorize button at all? Force-refresh /docs. The page caches the
    schema, and a copy from before 2026-08-23 has no security scheme in it.
    Confirmed present in openapi.json: securitySchemes.HTTPBearer, and
    /auth/me carries security=[{"HTTPBearer": []}].


401 on /auth/me — READ THE DETAIL, it names the cause
    Since 2026-08-23 each cause has its own message. The endpoint itself is
    fine; it was verified returning 200 for a correct access token while all
    of these returned an identical "Not authenticated", which is what made it
    look broken.

    "No bearer token"          the header never arrived. In Swagger /docs you
                               must click Authorize and paste the token —
                               calling /auth/login there does NOT apply it.
    "That is a refresh token"  login returns access_token AND refresh_token.
                               The second one is only for /auth/refresh.
    "Access token has expired" they last 15 minutes (ACCESS_TOKEN_EXPIRES_IN).
                               POST /auth/refresh with the refresh_token.
    "could not be verified"    truncated on copy, or the word Bearer pasted
                               into the value as well as the header.
    "no longer exists"         the account was deleted after the token was
                               issued. Tokens stay validly signed until they
                               expire, so the user is re-read every request.
    "This account is disabled" set disabled=false via PATCH /users/{id}.

403 "Requires one of: admin"
    Authentication worked; the role is wrong. Check GET /auth/me — a role of
    null means no permissions anywhere, which is what accounts created
    through POST /CRUD/register/ get.

404 on /auth/login
    That deployment predates the auth work. Check `git log --oneline -1`.

RuntimeError about JWT_PRIVATE_KEY at startup
    The env var is missing or is not valid base64-encoded PEM. Both local
    .env and the droplet's .env.production must have their own distinct pair.
